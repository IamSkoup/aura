# Aura Wear

Next.js-магазин кастомной одежды. Реализован первый сценарий с футболкой: Firebase Authentication → каталог Realtime Database → редактор слоёв и GLB/UV-предпросмотр → сохранение проекта → корзина → заказ → админская проверка и экспорт макета. Серверный сценарий от регистрации до экспорта макета проверен на локальных эмуляторах Firebase. При отсутствии платёжных ключей заказ остаётся **неоплаченным**.

## Бесплатная статическая версия на GitHub Pages

Адрес после публикации: **https://iamskoup.github.io/aura/**. Исходники статической версии находятся в `static-site/`; серверный Next.js в `src/app` сохранён. GitHub Actions собирает Vite-приложение с базовым путём `/aura/` и публикует `dist-pages/`. Внутренние адреса используют `#/catalog`, `#/studio` и другие hash-маршруты, поэтому обновление страницы работает на GitHub Pages. Модель `/models/aura-tee.glb` и изображение находятся в репозитории, а Three.js загружается только при открытии конструктора.

Это **демонстрация без заказов и оплаты**. Изображения загружаются и сохраняются в IndexedDB браузера вместе с проектами; они не попадают на сервер. Корзина хранится в localStorage. Очистка данных браузера или открытие другого устройства удаляет доступ к проектам. Сумма в корзине условная и не проверяется сервером. Производственный файл из статической версии не формируется. В Firebase статическая версия читает только опубликованные товары через клиентский SDK; при пустой или недоступной базе показывает явно помеченную демонстрационную футболку. Firebase Authentication доступна для входа/регистрации, но **не синхронизирует локальные проекты**.

Локальная проверка статической версии (Node.js 20+):

```bash
npm ci
npm run pages:dev
# открыть http://localhost:5173/aura/
npm run pages:build
npm run pages:preview
```

### Инструкция для владельца Aura Wear

**Публикация без расходов.** Репозиторий должен быть публичным, а GitHub Actions разрешены в его настройках. После push в `main` workflow `.github/workflows/pages.yml` сам проверит проект и попытается включить GitHub Pages (`enablement: true`), затем разместит демоверсию по адресу `https://iamskoup.github.io/aura/`. Результат смотрите во вкладке **Actions**. Если правила репозитория не позволят workflow включить Pages автоматически, один раз откройте **Settings → Pages → Build and deployment → Source: GitHub Actions**. Для этого не нужен Firebase Blaze, банковская карта или App Hosting. GitHub Pages подходит только для статической версии; Next.js API-маршруты там не выполняются.

**Firebase на бесплатном Spark.** В Firebase Console проекта `aurawear-4be25` включите Authentication → Sign-in method → Email/Password. В Authentication → Settings → Authorized domains добавьте `iamskoup.github.io` (без `/aura/`); для локальной разработки разрешите `localhost`. В Realtime Database опубликуйте правила из `database.rules.json` через вкладку **Rules** (или после проверки текущих правил выполните `npx firebase deploy --only database --project aurawear-4be25`). Правила разрешают только чтение опубликованных товаров с запросом `orderByChild('published').equalTo(true)`; записи из браузера закрыты. Статическая версия содержит только публичную конфигурацию Web SDK. Сервисные ключи Firebase Admin нельзя добавлять в GitHub, переменные `VITE_*` или статическую сборку. Следите за лимитами Spark: их превышение может ограничить доступность, поэтому бесплатность не является гарантией для большого магазина.

**Заполнение каталога.** Текущая футболка с пометкой «демо» не является товаром для продажи. Для реального каталога нужны подтверждённые название/SKU, цена, остаток, состав, размерная сетка, печатные зоны и качественные изображения с правом использования. В статической версии публичные фотографии можно положить в `public/images/` и указать в записи `products/<id>/image` путь `/images/имя-файла.webp`; после коммита GitHub Actions опубликует их. Не добавляйте фотографии клиентов или исходники принтов в публичный Git-репозиторий. Редактировать записи каталога можно через Firebase Console или защищённую серверную админку. Изображения вида `/api/public-assets/...` в статической версии недоступны, такие товары скрываются. Другим изделиям нужен свой GLB/UV-адаптер; до его готовности доступен только 2D-предпросмотр.

**Подключение ЮKassa.** Для реальной оплаты продавец заключает договор с ЮKassa, выполняет требования по чекам и получает Shop ID и секретный ключ. Затем размещает **серверную** Next.js-версию на хостинге с Node.js, указывает в его секретах `PAYMENT_PROVIDER=yookassa`, `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY` и `NEXT_PUBLIC_SITE_URL`. В кабинете ЮKassa задаёт HTTPS webhook `https://<домен>/api/payments/webhook`. Код в `src/app/api/payments/` создаёт платёж на сервере и при уведомлении повторно проверяет его через API ЮKassa, сумму, валюту и номер заказа; повторное событие не должно менять оплаченный заказ второй раз. До реальных продаж надо пройти тесты успешной и неуспешной оплаты, возврата и повторного webhook. Секретный ключ никогда не размещается на GitHub Pages. **Статическая версия ЮKassa не подключает и деньги не принимает.**

**Серверная обработка платежей и уведомлений.** Разверните Next.js-приложение с защищённым Firebase Admin-доступом (workload identity либо секрет `FIREBASE_SERVICE_ACCOUNT_JSON` в хостинге), Realtime Database и постоянным файловым хранилищем. Настройте HTTPS, домен, мониторинг ошибок и резервное копирование. Убедитесь, что webhook доступен снаружи и заказ меняет статус только после проверки у платёжного сервиса. GitHub Pages для webhook или API заказов не подходит.

**Файловое хранилище.** Для прототипа изображения остаются локально в IndexedDB; при чистке браузера они теряются. Для продажи нужны приватное хранение исходников и производственных файлов, резервные копии и доступ через проверенный серверный API. Серверный модуль `src/lib/storage.ts` поддерживает Firebase Storage (`STORAGE_PROVIDER=firebase`, `FIREBASE_STORAGE_BUCKET`) или S3-совместимый бакет (`STORAGE_PROVIDER=s3`, `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`). Firebase Storage и сторонние бакеты могут потребовать платный тариф или карту; проверьте актуальные условия до подключения. Не заменяйте оригиналы файлами предпросмотра.

**Доставка.** Получите от продавца географию продаж, перевозчика, тарифы, правила бесплатной доставки, сроки и адреса пунктов выдачи. Затем подключите расчёт на сервере в `src/app/api/orders/route.ts` и показывайте подтверждённую сумму до оплаты. Сейчас серверный пример использует нулевую предварительную стоимость доставки с последующим уточнением; это не готовая схема для реальных продаж. Проверьте передачу трек-номера и изменение статусов.

**Включение настоящих заказов.** Сначала заполните реальные товары и материалы, реквизиты продавца, контакты, доставку, политику обработки данных, оферту и возвраты для страны продаж. После утверждения документов заполните `settings/public` в Realtime Database и только тогда установите `legalReady=true`, `merchantReady=true`. Но этих флагов **недостаточно**: перед коммерческим запуском нужны постоянное хранение фото, серверная проверка цены, тестирование оплаты, учёт одновременных покупок/остатков, достоверная стоимость доставки, экспорт и проверка печатных макетов. Запускать продажи нужно на серверной версии, а не на GitHub Pages. Пока это не выполнено, демоверсия не создаёт заказов.

**Возможные расходы.** GitHub Pages и локальная демоверсия могут работать без оплаты в пределах правил и квот сервисов. Реальный магазин может потребовать платный Next.js-хостинг, объектное хранилище, домен, резервные копии, услуги доставки, онлайн-кассу и комиссию платёжного провайдера. Firebase Spark ограничен бесплатными квотами; Firebase App Hosting и некоторые варианты Storage могут требовать Blaze и платёжный аккаунт. Клиент выбирает и оплачивает эти сервисы самостоятельно.

## Быстрый запуск

Требуются Node.js 20+, npm и Java 21 для Firebase Emulator Suite.

```bash
git clone https://github.com/IamSkoup/aura.git
cd aura
npm ci
cp .env.example .env.local
```

В первом терминале запустите `npm run emulators`. Когда порты 9099 и 9000 будут готовы, во втором терминале выполните `npm run seed`, затем `npm run dev`. Тестовый каталог существует только в эмуляторе. Для Windows вместо `cp` используйте `copy` в cmd или `Copy-Item` в PowerShell.

Откройте `http://localhost:3000`. Зарегистрируйте пользователя через `/login`. Для локальной проверки админки назначьте роль **из отдельного терминала**, затем войдите повторно:

```bash
npm run grant-admin -- admin@example.test
```

Команда работает с эмулятором, если `.env.local` содержит `FIREBASE_AUTH_EMULATOR_HOST`. Для реального Firebase она требует учётную запись Admin SDK на сервере. Не размещайте её ключ в Git.

Эмулятор содержит только **тестовый товар** с условной ценой. Режим не предназначен для реальных платежей и заказов. В реальном проекте товары публикуются через `/admin/products` после ввода подтверждённых бизнес-данных.

## Структура

- `src/app` — страницы Next.js и серверные API.
- `src/components` — интерфейс, 3D-просмотр и редактор.
- `src/store` — история конструктора, корзина и избранное.
- `src/lib` — Firebase, хранение файлов, валидация, цены и платёжный клиент.
- `public/models/aura-tee.glb` — собственная UV-модель футболки; `scripts/create-shirt.py` — её генератор.
- `database.rules.json` — правила Realtime Database.
- `storage.rules` — запрет прямого доступа к исходникам в Firebase Storage; файлы выдаёт только сервер после проверки прав.
- `apphosting.yaml` — публичная конфигурация веб-приложения для Firebase App Hosting.
- `scripts/seed.ts` — тестовые данные только для эмулятора.

## Firebase и развёртывание

1. В проекте `aurawear-4be25` включите Authentication → Sign-in method → Email/Password и Realtime Database. В Authentication → Settings → Authorized domains проверьте, что добавлены `localhost` для местной разработки и ваш домен для публикации. Возьмите параметры веб-приложения из консоли и задайте переменные `NEXT_PUBLIC_FIREBASE_*` из `.env.example` на хостинге. Эти параметры публичны; серверные ключи там не размещайте.
   Для предоставленного проекта: `NEXT_PUBLIC_FIREBASE_PROJECT_ID=aurawear-4be25`, `NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN=aurawear-4be25.firebaseapp.com`, `NEXT_PUBLIC_FIREBASE_DATABASE_URL=https://aurawear-4be25-default-rtdb.europe-west1.firebasedatabase.app`, `NEXT_PUBLIC_FIREBASE_APP_ID=1:318217753716:web:37bd05522aca881615ad21`. Публичный Web API key скопируйте из Firebase Console в `NEXT_PUBLIC_FIREBASE_API_KEY`. Переменные `*_EMULATOR_HOST` на хостинге не задавайте.
2. Для запуска с настоящим Firebase создайте отдельный `.env.local` по образцу `.env.example`, замените локальные URL и ID на значения выше, задайте `FIREBASE_PROJECT_ID=aurawear-4be25` и `FIREBASE_DATABASE_URL` с HTTPS-адресом вашей Realtime Database. Удалите `NEXT_PUBLIC_FIREBASE_AUTH_EMULATOR_HOST`, `FIREBASE_AUTH_EMULATOR_HOST`, обе переменные `*_DATABASE_EMULATOR_HOST` и `FIREBASE_STORAGE_EMULATOR_HOST`. Предоставьте Firebase Admin SDK доступ через workload identity или приватный файл учётной записи, на который указывает `GOOGLE_APPLICATION_CREDENTIALS`. Храните этот файл вне репозитория.
3. После проверки и резервного копирования текущих правил установите новые: `npx firebase login`, затем `npx firebase deploy --only database --project aurawear-4be25`. Это меняет правила доступа существующей базы данных.
4. Самый короткий путь к публичному магазину: Firebase Console → App Hosting → создать backend → подключить GitHub `IamSkoup/aura`, ветку `main`, корень `/`. App Hosting собирает Next.js и обновляет сайт после push. Для этого может потребоваться план Blaze и привязанный платёжный аккаунт Google Cloud. Адрес появится в App Hosting после первого успешного развёртывания; GitHub Pages по адресу `iamskoup.github.io/aura/` серверные API не запускает.
5. В Firebase Console включите Storage и подтвердите имя бакета `aurawear-4be25.firebasestorage.app`. `apphosting.yaml` уже задаёт `STORAGE_PROVIDER=firebase` и публичную конфигурацию из веб-приложения. Опубликуйте правила `npx firebase deploy --only storage --project aurawear-4be25` после проверки существующих правил. Сервисная учётная запись App Hosting должна иметь доступ к Storage и Realtime Database.
6. Для другого Node.js-хостинга задайте `NEXT_PUBLIC_SITE_URL`, запустите `npm ci && npm run build && npm run start`. Серверу нужен ADC или секрет `FIREBASE_SERVICE_ACCOUNT_JSON` (полный JSON ключа, вводимый только в хранилище секретов хостинга). Альтернатива Firebase Storage — приватный S3-совместимый бакет с `STORAGE_PROVIDER=s3`, `S3_BUCKET`, `S3_REGION`, необязательным `S3_ENDPOINT`, `S3_ACCESS_KEY_ID` и `S3_SECRET_ACCESS_KEY`. В локальном эмуляторе файлы по умолчанию пишутся в `.data/assets`.

В Realtime Database прямые записи из браузера запрещены. Сервер проверяет Firebase ID token, админскую роль, варианты товара и цену. Админская роль назначается только через Admin SDK. Пользователь может читать лишь собственные проекты и заказы; опубликованные товары и шаблоны доступны всем.

## Оплата ЮKassa

1. Заключите договор с ЮKassa и настройте онлайн-кассу/чеки по требованиям продавца в России.
2. Задайте серверные `PAYMENT_PROVIDER=yookassa`, `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY` и адрес сайта в `NEXT_PUBLIC_SITE_URL`. Домен `api.yookassa.ru` должен быть разрешён на исходящие соединения.
3. Зарегистрируйте webhook `https://<ваш-домен>/api/payments/webhook`. Событие не принимается на веру: сервер повторно получает платёж из ЮKassa, проверяет ID заказа, сумму и валюту, после чего идемпотентно меняет статус.
4. Пройдите тестовый платёж, повторную доставку webhook и отказ до запуска. Тестовые платежи остаются в статусе ожидания реальной оплаты и исключены из подтверждённой выручки.

Пока платёжный провайдер не настроен, сайт честно создаёт заказ без списания и оставляет статус «Ожидает оплаты». Реальные деньги в этом режиме не принимаются. Администратор не может вручную перевести неоплаченный заказ в «Оплачен».

## Новая 3D-модель

Подготовьте GLB/glTF с UV-развёрткой печатной поверхности, физическими размерами зон и фотографиями изделия. Для футболки поверхность называется `Front_Print_Surface`/`Back_Print_Surface`, а генератор лежит в `scripts/create-shirt.py`. Добавьте для новой модели отдельный адаптер материалов/UV в компонент `Shirt3D`, конфигурацию зон и тарифов в базе, затем проверьте положение принта, переднюю и заднюю стороны и производственный экспорт. Пока адаптер для модели отсутствует, конструктор показывает 2D-изображение и сообщает об этом.

## Управление

После входа администратор использует `/admin/products` для товара и печатных зон, `/admin/templates` для авторских принтов, `/admin/orders` для заказов и экспорта и `/admin/setup` для инструкции подключения. Подтвердите права на все загружаемые дизайны. Исходные фото покупателей приватны. Экспорт создаётся в PNG с размером печатной зоны и DPI из базы; при недостаточном разрешении исходника экспорт прерывается.

## Что требуется до публичного запуска

Для приёма реальных заказов также нужно выставить `settings/public/legalReady=true` и `settings/public/merchantReady=true` в Realtime Database после утверждения документов и реквизитов. Там же заполните `merchantName`, `privacyPolicy`, `offer`, `returnPolicy` и `contactEmail`. До этого сервер отклоняет оформление вне эмулятора. Нужны реальные товары, цены, остатки, фото, мерки поставщика, состав/уход, требования типографии, тарифы доставки, контакты и реквизиты продавца, утверждённые правовые документы для России, Firebase Admin-доступ, файловое хранилище и договор с платёжным провайдером. Указанные данные в проекте не выдуманы. Функции остальных изделий требуют собственных GLB/UV-моделей либо подтверждённого 2D-просмотра и настроек вариантов.

## Текущие ограничения

- Готовые принты, отзывы и галерея пусты до публикации реальных материалов. Фотографии отзыва становятся публичными только после подтверждённой покупки, согласия покупателя и модерации.
- Остальные изделия требуют подготовленных моделей с UV-развёрткой и собственных адаптеров печати. В интерфейсе для них показывается 2D-изображение; полноценный просмотр принта на изделии пока не реализован.
- Нет бронирования остатков при одновременных заказах, расчёта доставки по тарифу перевозчика, применения промокодов, возвратов через платёжное API и переноса гостевой корзины в другой браузер. Эти функции нужны до коммерческого запуска.
- Производственный PNG задаёт размер зоны и DPI, но текстовый рендерер экспорта использует серверный шрифт. Перед печатью нужен тестовый образец и сверка начертания, цветов и требований типографии.
- Для первого запуска эмуляторов нужен сетевой доступ к `storage.googleapis.com`, откуда Firebase CLI скачивает исполняемый файл Realtime Database Emulator.

Проверки: `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`. Полный поток Firebase проверяйте с запущенными эмуляторами и опубликованными правилами.
